# GitSphere Methodology

GitSphere publishes three independent rankings for each of 250 countries and territories:

| Mode | Ranks | Limit per country | Pages | Data |
| :-- | :-- | --: | :-- | :-- |
| Top Repositories | public, non-fork repositories by stars | 100 | `rankings/<country>.md` | `data/<CC>.json` |
| Top Developers | individual users by public followers | 1,000 | `rankings/developers/<country>.md` | `data/developers/<CC>.json` |
| Top Contributors | individual users by public contributions, rolling 12 months | 1,000 | `rankings/contributors/<country>.md` | `data/contributors/<CC>.json` |

`data/summary.json` holds global scan progress and the status of every country in every mode.

## 1. Country attribution

GitHub has no country field. GitSphere attributes a **repository** to the public profile location of its owner (a user or an organization), and a **developer** to the public profile location of that user. Attribution is **not** a claim about citizenship, nationality, residence, IP address or legal incorporation.

All three modes use one resolver, `src/geo/resolver.js`. An account can therefore never be assigned to different countries by different rankings.

### Gazetteer

`geography/<CC>.json` is generated by `scripts/build-gazetteer.js` from:

- **Countries States Cities Database** (pinned release, SHA-256 verified, ODbL-1.0): country names and translations, subdivisions with ISO 3166-2 codes, cities.
- **GeoNames** (CC BY 4.0): `cities500` (places with population > 500, with population, feature codes and alternate/native names) and `admin1CodesASCII`. Countries with fewer than 500 places in `cities500` are supplemented from their full GeoNames country dump: populated places only, most notable first, capped at 6,000 per country.
- Localized country names from the ICU data in Node.js (`Intl.DisplayNames`, 70+ locales).
- A short reviewed list in `src/geo/curated.js`: non-geographic terms ("Remote", "Earth", "localhost"), supranational regions ("Europe", "APAC"), a few metro nicknames ("Bay Area"), and territories that upstream data duplicates as subdivisions (e.g. Hong Kong under China).

The gazetteer covers more than 700,000 places and 5,800 subdivisions. No finite gazetteer covers every settlement or every way people write a location.

### Resolution rules

A location is normalized (Unicode NFKD, Latin diacritics folded, native-script marks preserved), split into segments (`,` `/` `|` `;` parentheses, ` - `), and each segment is matched against country names, ISO codes and flag emoji, subdivision names and codes, and places. Then, in order:

1. **Explicit country.** One unambiguous country name, ISO code or flag emoji → that country (high confidence). Two different explicit countries (`Sri Lanka / Australia`) → **ambiguous**, never forced.
2. **Place + subdivision.** `Portland, OR`, `Redmond, WA`, `Colombo-PR` resolve when the place lies in that subdivision. If several countries match (`San Francisco, CA` also matches villages in subdivisions coded `CA` elsewhere), the clearly dominant match (≥10× population) wins.
3. **Consistent places.** Several segments that only share one candidate country (`Tbilisi, Georgia`) → that country.
4. **Single place.** A place found in one country only → that country (medium). A name found in several countries resolves only if the top match is a major place (≥1M population, or the score of a subdivision or country name) **and** at least 10× more significant than any other country's match. `London` → GB; `Portland`, `Hyderabad`, `Punjab`, `Colombo` stay **ambiguous**.
5. **Weak country names.** A country name that is also a foreign subdivision (`Georgia`: GE and US-GA) needs context. A bare two-letter code that is also a subdivision code (`CA`, `DE`, `IN`) is ambiguous.
6. **Transliteration.** For South Asian countries, a fallback key folds aspirated romanizations (`Mathugama` ↔ `Matugama`).
7. Empty, fictional, remote-only and supranational locations are **unknown**.

Each attributed record stores `attribution: { code, confidence, evidence }`. Ambiguous and unknown accounts are counted in run reports and excluded from rankings.

## 2. Discovery

GitHub search returns at most 1,000 results per query. GitSphere never treats a capped query as complete.

### Partitioned search (`src/discovery/partitions.js`)

A partition is a metric range (stars, followers or public repositories) plus an optional creation-time range. A partition with more than 1,000 results is split:

1. by **metric**: geometric bisection for wide ranges, arithmetic for narrow ones, highest values first;
2. once the metric is a single value (an *exact bucket* such as `stars:215`), by **creation time**, bisecting down to 60 seconds.

Children never overlap and exactly cover their parent. A partition that still exceeds the window at the minimum time span is recorded as **unresolved** with its reported count. It blocks certification below its metric value instead of being dropped. Queries that fail three times are recorded the same way. The queue and pagination cursor are checkpointed after every page.

### Continuous global scans (`src/discovery/metric-scan.js`)

- **Repositories:** `fork:false sort:stars-desc`, down to a floor (default 50 stars).
- **Developers:** `type:user sort:followers-desc`, down to a floor (default 100 followers).

Each scan runs in **cycles**. When a cycle's queue empties, the cycle is recorded and the next one starts immediately. Stars, followers, renames, transfers, location changes and newly eligible repositories are re-observed every cycle. The *verified floor* is the lowest metric value down to which every result has been enumerated. It is the better of the last completed cycle (if under 21 days old) and the in-progress cycle, raised above any unresolved partition.

### Location discovery (`src/discovery/location-scan.js`)

Global floors cannot reach the top repositories and developers of smaller ecosystems. For every country, GitSphere searches `location:"<term>" type:user` (partitioned by followers) and `location:"<term>" type:org` (partitioned by repositories). Search terms are the country's names, subdivisions and most populous places. A term is used only if the shared resolver itself attributes it to that country. Each account found is attributed by the resolver, never by the search term, so "Colombo, Brazil" found via "Colombo" lands in Brazil.

Countries are visited round-robin with a fixed per-country request slice, so large countries cannot starve small ones. A country that finishes a round rests for 14 days before the next refresh round. Users found this way include low-follower accounts, which feed the contributions ranking.

### Owner expansion, revalidation and refresh

- Owners with more than one public repository whose top repository could enter their country's ranking have up to 30 repositories fetched.
- Before publication, ranked repositories are re-fetched by **stable node ID**. Deleted, private and forked repositories are removed. Renames and transfers are followed, and a repository whose owner moved is re-attributed.
- Ranked developers are refreshed by node ID weekly. Deleted accounts are removed and relocated accounts move country.
- Records migrated from the pre-GitSphere dataset carry no node ID. They are marked *pending revalidation*, resolved to node IDs by name, and dropped if missing. A ranking containing them is never Published.

## 3. Rankings

- **Repositories:** stars desc, then forks desc, then name, then node ID. Archived repositories stay listed and are marked.
- **Developers:** followers desc, then public repositories, then login, then node ID. Organizations are excluded.
- **Contributors:** public contributions desc, then commits, followers, login, node ID.

### Public contributions

GitSphere queries `contributionsCollection(from, to)` for a rolling window of exactly one year ending at the measurement hour, and records the window and measurement time. GitHub's GraphQL schema describes `contributionCalendar.totalContributions` as "the count of total contributions in the calendar", and `restrictedContributionsCount` as "a count of contributions made by the user that the viewer cannot access. Only non-zero when the user has chosen to share their private contribution counts".

**Public contributions = calendar total − restricted contributions.** This counts commits, issues, pull requests, reviews and repository creation, as GitHub's contribution calendar does. It is not a commit count and not a lifetime total. Private contribution counts are never ranked or published, beyond noting how many were excluded.

Contribution candidates are every discovered user in a country, not just the most-followed. Never-measured accounts are measured first (most public repositories first), interleaved across countries. A developer with few followers but many public contributions is therefore eligible. GitSphere cannot enumerate every GitHub account, so the contributions ranking is never described as exhaustive.

## 4. Statuses and certification

Each country has exactly one status per mode, so status totals always equal 250.

| Status | Meaning |
| :-- | :-- |
| 🟢 Published | Coverage established: the global scan's verified floor is at or below the ranking's cutoff with a full ranking, **or** location discovery for the country finished a round without unresolved partitions (and, for repositories, without pending owner expansions). No pending legacy records. |
| 🟡 Provisional | Verified results exist; discovery is still running. |
| 🔵 Building | No results yet; discovery for the country is in progress. |
| 🟠 Stale | Results exist, but some have not been re-verified within 14 days. |
| ⚪ No attributable results | Discovery finished and found no account whose location attributes unambiguously to the country. Nothing is fabricated. |
| 🔴 Blocked | Discovery for the country is failing repeatedly. |

A country is never kept in Building just because it has fewer than 100 repositories or 1,000 developers. Contributors are Published only when every discovered account has been measured and location discovery finished without gaps. Even then, coverage is limited to discovered accounts.

Certification is bounded by what the scans establish. GitHub search results are mutable, and stars, followers and locations change between observations. Every dataset records `updatedAt` (last content change) and `verifiedOn` (oldest verification of a listed entry).

## 5. Automation

`.github/workflows/pipeline.yml` runs hourly with one data writer (`concurrency: gitsphere-data-<ref>`, never cancelled mid-run, shared with the geography sync). Each run:

1. spends a bounded GraphQL budget (default 900 requests with a 300-point reserve) across: global repository scan, legacy resolution, location discovery, follower scan, owner expansion, revalidation, account refresh and contributions;
2. checkpoints after every page and batch, flushing the registry before the scan state so a checkpoint never runs ahead of the data;
3. stops cleanly on budget, runtime, primary or secondary rate limits;
4. publishes data, pages and directories (timestamps change only when content changes);
5. runs a secret scan of all generated files, commits once, rebases onto newer commits, and refuses to overwrite on conflict;
6. **fails the job if the run made no useful progress** (no requests with budget available, or requests without progress), after committing its checkpoints.

Pushes made with `GITHUB_TOKEN` do not trigger workflows, so the pipeline cannot loop.

## 6. Security

All GitHub metadata is untrusted. `src/core/sanitize.js` strips control and bidirectional-override characters, truncates fields and redacts credential-shaped strings (GitHub, AWS, Slack, Stripe, Google, npm, PyPI, GitLab and SendGrid tokens, JWTs, private keys, credentials in URLs). Every persisted file passes through a guard that refuses to write credential-shaped content and names only the file and pattern, never the value. Only fields needed for ranking and display are stored. Homepage URLs and other free-text fields are not persisted. See [`SECURITY.md`](../SECURITY.md).
